- 2026-08-01 — **Chatbot-as-a-Service: replaced the single-shot prompt with a tool-calling agent (Phase 1 — web widget + admin test panel only).** Fixes the reported bug where the chat reply was inaccurate while the product carousel was correct.
  - Root cause: `ChatbotController` built the prompt from a 12-product shortlist (`ChatbotCatalogSelector.BuildPromptSet`) whose pinned ids came from `ChatProfile.LastShownProductIds`, which was itself set to the *previous* turn's shortlist. From turn two the carried-over ids filled the whole budget before the current query's matches were considered, so the model answered from stale products while the carousel — which re-ranked from scratch via `ChatbotCardPolicy` — showed the right ones.
  - Added `IAgentAiProvider` (`Application/Common/Interfaces/IAgentAiProvider.cs`) — tool-calling contract (`AgentTool`/`AgentToolCall`/`AgentMessage`/`AgentStepResult`), separate from `IAiProvider.HandleConversationAsync` which the tenant RAG pipeline still uses. Implemented by `OpenAiProvider.RunAgentStepAsync` (OpenAI `tools`/`tool_calls` wire format) and `MockAiProvider.RunAgentStepAsync` (deterministic: searches once, then answers). Both registered against both interfaces in `Infrastructure/DependencyInjection.cs`.
  - Added `Application/Chatbot/Agent/`: `ChatbotAgentTools` (5 tools — `search_catalog`, `get_product_details`, `update_cart`, `save_customer_details`, `place_order` — plus their server-side execution and the thinking one-liners), `ChatbotAgentPromptBuilder` (static cacheable prefix + per-turn dynamic suffix), `ChatbotAgent` (the loop; capped at 4 model calls / 8 tool calls per turn, final iteration runs with no tools to force prose).
  - Catalogue is no longer inlined in the prompt. The model gets a **category index** (name, count, price band) and calls `search_catalog` for anything specific. Measured prompt size: ~570 tokens at 50 products and ~570 at 2,000 — flat, where the old shortlist design grew with what it inlined and still only showed the model 12 of N products.
  - Cards now come from what the model actually looked up this turn instead of a separate ranker, so reply and carousel cannot disagree. `LastShownProductIds` is retained **only** for id resolution on follow-ups ("add the second one") and is never fed back into prompt selection.
  - `place_order` is terminal — the agent returns a `ChatbotOrderIntent` and `ChatbotController` creates the order from the server cart, so order number/total/Razorpay stay server-generated. `update_cart` replaces the hand-parsed `cart_ops` JSON envelope; `save_customer_details` replaces the `ExtractedName`/`Phone`/`Address` scraping. Removed `ChatbotController.LegacyCartAsOps`; `RecordTokenUsageAsync` now takes explicit token counts (one row per turn, not per model call).
  - `POST /chatbot/{apiKey}/message` gained a second response shape: NDJSON (`{"type":"thinking"}` per tool call, then `{"type":"final","payload":…}`) when the caller sends `Accept: application/x-ndjson`; otherwise the byte-identical legacy JSON object, so third-party sites running a cached older `chatbot-widget.js` keep working. The non-streaming payload also gained a `thinking` string array.
  - `frontend/public/chatbot-widget.js`: requests NDJSON, reads the body incrementally (`readStream`), renders each thinking line into the typing bubble (`setThinking`, `.rc-think` style); falls back to the single-JSON path where `ReadableStream`/`TextDecoder` are missing. Turn handling extracted into `applyTurn` so both paths share it. `frontend/src/pages/admin/AdminChatbotClientDetailPage.tsx` lists the returned `thinking` steps above the reply.
  - **Not migrated (deliberate):** `ChatbotClientWebhookHelper` (WhatsApp/Messenger/Instagram) still uses `ChatbotPromptBuilder` + `ChatbotCatalogSelector` + `ChatbotCardPolicy` and therefore still has the stale-shortlist behaviour — those classes are live, do not delete them. Phase 2 = channels onto `ChatbotAgent` with `CanPlaceOrders: false`; phase 3 = tenant storefront chatbot (§4.7).
  - **Latency note:** a turn is now 2-3 model round-trips instead of 1 (~1.5-3s on `gpt-4o-mini`); the streamed thinking lines are what make that read as progress rather than as a hang.
- 2026-08-01 — **Fix: streamed chatbot responses serialised PascalCase, breaking the product carousel.** `ChatbotController.WriteEventAsync` called `JsonSerializer.Serialize(payload)` with library defaults (PascalCase) instead of the MVC pipeline's web defaults (camelCase), so NDJSON turns shipped `Title`/`ImageUrl`/`Price` to a widget reading `title`/`imageUrl`/`price` — every card rendered as undefined/null. Added a `StreamJson` options instance mirroring `Program.cs` `AddJsonOptions` (web defaults + `JsonStringEnumConverter`). Only affected the streamed path introduced earlier today; the non-streaming `Ok(...)` shape and the WhatsApp/Messenger/Instagram channels were never affected.

Host is a full-viewport `position:fixed` overlay with `pointer-events:none`; only the launcher, teaser and panel re-enable pointer events. - 2026-08-01 — **Fix: product carousel collapsed to a bare scrollbar, and the composer rendered a native scrollbar** (`frontend/public/chatbot-widget.js`). Both regressions from the Shadow DOM rewrite earlier today.
  - Carousel: `.msgs` is a column flex container and `.rail` is a horizontal scroll container. A scroll container's automatic minimum size is `0` (not `min-content`), so the rail was shrunk to nothing and only its scrollbar remained visible. The pre-rewrite `.rc-scroller` had `flex-shrink:0`; that pin was lost in the rewrite. Restored via `.msgs > *{flex:0 0 auto}` plus an explicit `flex:0 0 auto` on `.rail`. Also gave `.card .ph` an explicit `height:150px` alongside `aspect-ratio`, since aspect-ratio alone leaves older WebViews at zero height.
  - Composer: `autoGrow()` ran at bootstrap while the panel was still `display:none`, so `scrollHeight` was 0 and the textarea was pinned to `height:0px` — which is why a native vertical scrollbar (the stacked arrows) appeared over the field. `autoGrow()` now bails when `scrollHeight` is 0, clamps to a 34px floor, and toggles `overflow-y` to `auto` only past the 96px cap; the bootstrap call was dropped and `doOpen()` calls it at first measurable layout instead. Textarea defaults to `overflow-y:hidden`.
  - Hid `::-webkit-scrollbar-button` on `.msgs` and `.rail` (native arrow buttons were showing through on Windows).
  - Added 5 CSS-level regression assertions to `frontend/test/chatbot-widget.test.mjs` (34 total). Verified they fail against the broken build and pass against the fix — jsdom has no layout engine, so these assert the CSS rules rather than geometry.
- 2026-08-01 — **Widget now tolerates PascalCase responses (backend/widget version skew).** After the streamed-serialisation fix landed in source, a running-but-not-yet-rebuilt API still returned `Title`/`Price`/`ImageUrl`, which rendered the carousel as blank ₹0 cards — the data was all present, only the casing differed. `chatbot-widget.js` now runs every network payload through `camelKeys()` (recursive first-letter lower-casing) at three boundaries: `applyTurn`, `setCart` and `loadConfig`. This matters structurally, not just for this incident: the widget is loaded directly by third-party sites with no version coupling to the API, so new-widget/old-server and old-widget/new-server skew are both permanent conditions. Warns once via `console.warn` when PascalCase is seen, so a stale deploy still surfaces rather than being silently masked. Added 5 test assertions covering a PascalCase turn (39 total); verified they fail without `camelKeys` and pass with it.
- 2026-08-01 — **Fix: card "Add" and card-tap were dead; product detail restored to a full in-panel view** (`frontend/public/chatbot-widget.js`).
  - Root cause of both: the carousel's drag-to-scroll called `rail.setPointerCapture()` on `pointerdown`. While a pointer is captured the browser retargets the following `click` to the capturing element, so every click inside a card landed on the rail and neither the Add button nor the card body ever fired. Capture is now taken only after the pointer moves past the 5px drag threshold — which a plain click never crosses — so clicks are untouched and drag-to-scroll still works. Also ignores non-primary buttons and stray pointer ids.
  - Product detail moved from a bottom sheet back to a full in-panel overlay (`.detail`, `position:absolute; inset:0` inside the panel) with a sticky Back bar and a sticky action row, matching the pre-redesign behaviour. The cart deliberately stays a bottom sheet — it is a short list and benefits from keeping the conversation visible. `openDetail`/`closeDetail` are now separate from `openSheet`/`closeSheets`; Escape and order placement close both.
  - Added test coverage that was missing: Add-from-card actually posts to `/cart`, a simulated drag does NOT open the detail view, a plain tap does, and Back closes it. 44 assertions total.
- 2026-08-01 — **Fix: vertical scrolling froze while the cursor was over the product carousel** (`frontend/public/chatbot-widget.js`). The rail carried a `wheel` handler (inherited from the pre-redesign widget) that mapped vertical wheel onto horizontal scroll and only released it at the rail's extremes — so hovering a card stopped the conversation from scrolling. More noticeable after the redesign because the taller cards make the rail a much larger hit target. Handler removed entirely: vertical wheel now falls through to the message list, while Shift+wheel, trackpad swipes and touch already scroll the rail natively. To keep horizontal scrolling discoverable for plain-mouse users (drag-to-scroll alone is not obvious), added prev/next arrow buttons in a new `.railwrap` container — hidden when the cards fit, and each arrow hides at its own end. Added 7 assertions (51 total), verified to fail if the wheel hijack is reintroduced.
- 2026-08-01 — **Removed all credentials from the committed `appsettings.json`** (`backend/src/ReplyCart.Api/`). GitHub push protection blocked a push on the OpenAI key at `appsettings.json:15`; investigation showed the key was already present on `origin/main` and four other remote branches (introduced by `2689ac6`/`2f49dee`), so this was a long-standing leak rather than a new one. Push protection only blocks high-confidence partner patterns, which is why the Meta app secret, Cloudflare token, JWT signing key, Cloudinary secret and Razorpay test keys were never flagged despite sitting in the same file.
  - 13 secret values blanked in the tracked file: `ConnectionStrings:DefaultConnection`, `Jwt:Secret`, `AI:OpenAI:ApiKey`, `Storage:Cloudinary:ApiKey`/`ApiSecret`, `Razorpay:KeyId`/`KeySecret`, `WhatsApp:AccessToken`/`VerifyToken`, `Meta:AppSecret`, `GoogleAnalytics:ServiceAccountPrivateKey`/`ServiceAccountPrivateKeyId`, `Cloudflare:ApiToken`, `Redis:AccessKey`. All 50 config keys retained; only values changed, so binding is unaffected.
  - Real values moved to `appsettings.Development.json` (already gitignored via `.gitignore:9`) so local dev keeps working with no setup. Added tracked `appsettings.Development.example.json` as the template for new developers.
  - Production reads them from Azure App Service application settings using `__` in place of `:` (e.g. `AI__OpenAI__ApiKey`); env vars outrank both JSON layers. **`appsettings.json` must be deployed with App Service settings already populated, or the app will fail at startup** — `Jwt:Secret` in particular throws when shorter than 32 chars, which is deliberate fail-fast behaviour.
  - Non-secret identifiers deliberately left in place: `Meta:AppId`, `Cloudflare:ZoneId`/`AccountId`, `Storage:Cloudinary:CloudName`, `Redis:Endpoint`, `GoogleAnalytics:ServiceAccountEmail`.
  - **Rotation is the actual mitigation, not this commit** — the secrets remain in git history on `main` and several feature branches. Documented in `context.md` §4.5.1.
